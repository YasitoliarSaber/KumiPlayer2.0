## 0. 先纠一个术语（用户 2026-10-03 指出）

`README.md` 第 108 行写的「安装版用户首次启动时选择**外部播放器**」是错误的表述，会让人误以为 KumiPlayer 会去启动别的播放器软件。

正确表述是「**内置播放器 · 外部整合包**」：

- KumiPlayer 的播放能力始终是「**内置播放器**」——由 KumiPlayer 自己构造 mpv 命令行、自己解析运行时路径、自己用 JSON IPC 管理进度与队列。这个身份不因运行时来自哪里而改变。
- 区别只在于**运行时与配置的来源**：内置模式用项目自带的干净 MPV 与自有配置；外部模式用用户本机某个 MPV 整合包的目录/可执行文件。
- 所以外部模式在**形式上**是外置的（mpv.exe 不在应用目录内），但在**工程语义上**它仍然是这个项目的内置播放器，只是套了别人的整合包。

对应代码现状（供后续统一命名参考）：

| 层 | internal（自带运行时） | external（外部整合包） |
|---|---|---|
| 后端 | `backend/app/playback/mpv_runtime.py` 内置解析 + `--config-dir` / `--include` / `--script` 注入 | `resolve_external_mpv_path()` / `inspect_external_mpv()`，不注入配置与脚本 |
| 前端 API | `src/api/config.ts` 注释 `internal = KumiPlayer 内置干净 MPV` | `external = 用户自备 MPV 整合包` |
| 设置页 | `src/pages/PlayerTuningPage.tsx` 选项 `内置播放器` | 选项 `外部 MPV 整合包` |
| 首启引导 | `src/pages/FirstRunSetup.tsx` `播放器已随应用提供` | 标签 `外部播放器`（**此处标签同样需要改成「外部整合包」**） |

建议统一成一组词：`内置 MPV（应用自带）` / `内置播放器 · 外部整合包`，并废弃「外部播放器」这一说法。

## 1. 结论速览（对应问题：这个 mpv 二进制允许分发吗）

**可以分发，而且不需要改成 libmpv。** 依据与义务如下：

1. **本项目这套 mpv 运行时是 GPLv2+ 许可的**，不是 LGPL。已在**本机二进制**上直接取证（见第 2 节），不是推测。
2. GPLv2+ 明确允许**原样再分发**（GPLv2 第 1、3 条）。所以「能不能带上别人的 mpv 一起发给用户」——能。
3. 但 GPL 的再分发**附带义务**，不做就违法。原样再分发时至少要满足：
   - 随包提供**许可证正文**（GPLv2，本项目已有 `mpv/licenses/mpv-v0.41.0/LICENSE.GPL`）；
   - 提供**完整对应源码**，或提供**有效期不少于 3 年的书面源码提供承诺**（GPLv2 第 3(a)/3(b) 条）；
   - 保留版权与许可证声明，不得附加额外限制。
4. **KumiPlayer 自身不需要跟着 GPL 开源**。因为它是**独立进程 + JSON IPC** 驱动 mpv.exe，不与 mpv 链接、不共享地址空间、不复制其代码，属于 GPL 意义上的「单纯聚合」（mere aggregation），而不是衍生作品。这一条已在本项目代码上核实：`src-tauri/src`、`backend/app`、`src/` 全文检索 `libmpv` / `libmpv-2.dll` **零命中**；播放由 `subprocess` 启动 `mpv.exe` 并传 `--input-ipc-server` 实现。
5. **别人套一层 libmpv 不是许可证要求，而是技术选择**。原因见第 4 节：libmpv 用于把播放器画面嵌进自己的窗口，代价是「同一进程内链接」——若用 GPL 版 libmpv，他们的整个应用就被传染成 GPL，所以他们通常特意改用 **LGPL 版 libmpv**（`mpv-dev-lgpl`）来规避。本项目的进程外方案在许可证上**比 libmpv 更省事**，代价是窗口无法内嵌、需要自己做进程生命周期管理。
6. **剩余的合规缺口不在二进制本身，而在材料**：`mpv/licenses/` 目前只有 6 份第三方许可证，缺 FFmpeg 与其余运行时 DLL 的许可证正文与组件登记，也没有书面源码提供承诺。这就是 `runtime-manifest.json` 里 `distribution_status = development-only` 的原因，也是 `stage_mpv_runtime.ps1` / `verify_installer_bundle.ps1` 双层拦截安装包的原因。
7. **另有独立于 GPL 的风险**：编解码**专利**（H.264 / H.265 / AAC 等）不由 FFmpeg 的 GPL 授权覆盖。个人/小范围分发通常无人追究，商业化分发需要单独评估。这一点与「用不用 libmpv」无关。

## 2. 取证：这套运行时到底是 GPL 还是 LGPL

网络上流传「官方 mpv Windows 构建是 LGPLv2.1」的说法（例如 winget 里那条 `mpv-v0.41.0-x86_64-pc-windows-**msvc**.zip` 条目标注 LGPLv2.1）。**本项目用的不是那个包**，而是 `mpv-v0.41.0-x86_64-w64-mingw32.zip`，两者许可证不同。以本机实际文件为准：

### 2.1 mpv.exe 自报运行特性里带 `gpl`

```text
$ mpv/runtime/mpv.com --version
mpv v0.41.0-dev-g41f6a6450 Copyright © 2000-2025 mpv/MPlayer/mplayer2 projects
 built on Dec 21 2025 19:19:52
libplacebo version: v7.358.0
FFmpeg version: git-2025-12-21-1fcb201
...

$ mpv/runtime/mpv.com -v --version
[cplayer] Configuration: -Dlibmpv=true -Dtests=true ... -Dbuildtype=debugoptimized ...
[cplayer] List of enabled features: build-date cplugins cuda-hwaccel cuda-interop d3d-hwaccel
  d3d11 d3d9-hwaccel debug direct3d dos-paths ffmpeg ffnvcodec gl gl-dxinterop gl-dxinterop-d3d9
  gl-win32 glob glob-win32 gpl javascript lcms2 libass libavdevice libplacebo luajit shaderc
  spirv-cross vector vk-khr-display vulkan wasapi win32 win32-desktop win32-executable
  win32-threads zlib
```

特性列表里的 **`gpl`** 表示该构建启用了 GPL-only 代码路径。

### 2.2 FFmpeg 三个 DLL 内嵌的配置串带 `--enable-gpl`

直接从 `avutil-60.dll` / `avcodec-62.dll` / `avformat-62.dll` 提取到的构建配置：

```text
--enable-gpl --enable-cross-compile --cross-prefix=x86_64-w64-mingw32- --arch=x86_64
--cc='ccache x86_64-w64-mingw32-gcc-posix' --cxx='ccache x86_64-w64-mingw32-g++-posix'
--disable-static --enable-shared --disable-doc --disable-programs --enable-muxer=spdif
--enable-encoder='mjpeg,png' --enable-libdav1d --enable-vulkan --enable-libshaderc
```

FFmpeg 官方说明：不加 `--enable-gpl` 时是 LGPLv2.1+；**一旦 `--enable-gpl`，整个 FFmpeg 变为 GPLv2+**（未同时启用 `--enable-version3` 时为 v2+，未升级到 v3）。

### 2.3 上游 mpv 自己的许可声明（`mpv` 源码 `Copyright`，v0.41.0）

> mpv as a whole is licensed under the GNU General Public License GPL version 2 or later (called GPLv2+ in this document, see LICENSE.GPL for full license text) by default. The mpv program is licensed the GNU Lesser General Public License LGPL version 2 or later (LGPLv2.1+ in this document, see LICENSE.LGPL for full license text) if built without using any GPL only files.
>
> …Linked libraries still can affect the final license (for example if FFmpeg was built as GPL).

**结论：本项目这一套 `mpv/runtime/` 整体按 GPLv2+ 处理。** 这也解释了为什么 `mpv/licenses/mpv-v0.41.0/` 里同时放了 `LICENSE.GPL` 与 `LICENSE.LGPL`——mpv 源码同时带这两份，但实际构建只适用其中一份。

## 3. 两套播放方案：分发与许可证差异（用户强调「有两套方案」）

这两套方案**不是许可证上的二选一**，而是产品形态上的两条运行路径，它们的合规工作量完全不同。

### 方案 A：内置 MPV（应用自带干净运行时）

| 维度 | 内容 |
|---|---|
| 分发物 | `mpv.exe`、`mpv.com`、24 个 DLL、2 个注册脚本，共 27 个运行文件 + `portable_config/` + `kumiplayer/` + `runtime-manifest.json` |
| 许可证 | **GPLv2+**（mpv 与 FFmpeg 均为 GPL 构建） |
| 谁承担义务 | **KumiPlayer 成为 GPL 软件再分发者**，需附 GPLv2 正文 + 源码（或书面提供承诺） |
| KumiPlayer 自身 | 进程分离 → 非衍生作品 → **不需要**改许可证 |
| 工作量 | 补齐许可证正文、组件登记、源码提供承诺、清单哈希复核 |
| 现状 | 已实现且在源码/开发版可用；安装包分发被 `distribution_status` 门控拦截 |

### 方案 B：内置播放器 · 外部整合包

| 维度 | 内容 |
|---|---|
| 分发物 | **不携带任何 mpv 二进制**；仅携带 KumiPlayer 自有层（`kumiplayer/` 脚本、强制配置、Anime4K 着色器）与后端代码 |
| 许可证 | KumiPlayer **不是 mpv 的再分发者**；用户自备整合包并自行承担其许可证 |
| KumiPlayer 自身 | 同样不涉及链接；自有脚本是 KumiPlayer 自己的代码 |
| 工作量 | 仅需保持「不注入、不改写整合包」的实现契约与检测/引导文档 |
| 现状 | 已实现（`external` 模式），可作为**不补齐任何材料即可对外发布**的路径 |

### 6 个需要注意的分界点

1. **`config/kumiplayer/` 自有层在任何方案下都随包分发**——它是 KumiPlayer 自己的配置与 Lua 脚本，不是第三方资产；但它写的是 mpv 的选项与 fn 绑定，属于「与 mpv 配合使用」，不算 mpv 衍生代码。
2. **Anime4K 着色器是 MIT**，随包分发无额外义务，只需保留许可证（已有 `mpv/licenses/anime4k-v4.0.1/LICENSE`）。
3. **`uosc_danmaku` 与 danmu_api 是另一条独立合规线**：`docs/THIRD_PARTY_NOTICES.md` 已说明 danmu_api 是 **AGPL-3.0** 且**不随包分发**、仅由用户自部署并 HTTP 调用——这条边界必须继续保持，否则 AGPL 义务会直接落上来。
4. **外部模式下不要注入 KumiPlayer 自有脚本**。`mpv/README.md` 已给出语义依据（`--include` 是覆盖语义、`--script-opts` 是覆盖语义），且当前实现确实不注入。这一点要作为长期契约守着：一旦注入，就变成「把自有代码加载进第三方运行时」，虽然仍是聚合关系，但会引发「是否会改写整合包行为」的连带讨论。
5. **两条路径的「中间态」风险**：方案 B 下 KumiPlayer 仍会生成 mpv 命令行，命令行里带的是受控参数（IPC、标题、受控播放列表、`--save-position-on-quit=no` 等）。这些参数不构成对 mpv 源码的修改，不产生 GPL 义务。
6. **同一条许可证逻辑不因「谁下载」而改变**：若改成「首次运行时从上游自动下载 mpv」，KumiPlayer 仍是「自动下载官方构建」而非自行再分发，GPL 的再分发义务会转移给上游 GitHub；但这只适用于能从上游公开地址取到、且用户可验证哈希的场景（本项目 `runtime-manifest.json` 已记录 `artifact_url` 与 `artifact_sha256`，具备这个条件）。

## 4. 为什么「别人都套 libmpv」——以及本项目为什么不必须

`libmpv` 是把播放器做成**库**的形态，宿主应用在同一进程里链接它，从而：

- 能把自己的窗口/纹理交给 mpv 直接渲染（内嵌播放画面、自绘 UI 覆盖在视频上）；
- 能拿到精确到帧的回调与逐帧控制；
- 缺点：**库与宿主同进程 → 许可传染**。若用 GPL 版 libmpv，宿主应用必须整体 GPL。

因此常见做法分化成两条：

- 想要内嵌画面、又不开源 → 用 **LGPL 版 libmpv**（`mpv-dev-lgpl-*.7z` / `-Dgpl=false`），代价是失去部分功能（Linux X11 输出、部分硬件解码等），并且要满足 LGPL 的「可替换库」要求；
- 只想控制播放、不要求画面内嵌 → **外部进程调用**，即本项目方案：许可上最干净（聚合而非衍生）、构建与升级最简单（换目录即升级）。

所以本项目「直接用 mpv.exe」不是次选，而是在「窗口不内嵌」这一前提下**许可证成本最低**的正解。唯一要接受的产品代价是：mpv 是独立窗口，KumiPlayer 的 UI 无法叠加在视频画面上，窗口行为需要额外处理（项目已用 `_strip_dwm_border()`、窗口样式与 uosc 配置处理）。

## 6. 推荐的 mpv 存放位置

### 6.1 结论

**三层存放，各司其职；源码仓库里不提交二进制。**

| 位置 | 放什么 | 是否进 Git | 理由 |
|---|---|---|---|
| `mpv/runtime/`（源码工作区） | 27 个运行文件 | **否**（现状已正确，仅跟踪 `README.md`） | 102 MB 二进制会永久污染 Git 历史；`.gitignore` 现在是「忽略实际文件、保留 README 与三份清单」，设计正确 |
| `mpv/licenses/` + 清单 JSON | 许可证正文、来源/版本/哈希登记 | **是** | 合规材料是文本，体积小，必须随源码可见、可审阅 |
| GitHub Release 资产 | `KumiPlayer-Setup.exe`（内含 `runtime/mpv/`） | 不进 Git | Release 支持单文件 ≤2 GB，是分发大体积产物的正确位置 |
| 构建机本地 / CI 缓存 | 官方 ZIP 解压后的运行文件 | 否 | 可从上游 ZIP + 清单哈希确定性重建 |

### 6.2 为什么不推荐 Git LFS

- LFS 只是把二进制挪出主对象库，**不解决 GPL 合规材料问题**，也不减少 clone 时的实际流量；
- 公开仓库的 LFS 流量计入仓库所有者配额，看板克隆会持续消耗；
- 一旦有人省略 LFS、或 LFS 对象被误删/过期，构建会突然缺文件；
- 本项目已具备更好的替代：`runtime-manifest.json` 记录了 `artifact_url` + `artifact_sha256` + 逐文件 SHA-256，**完全可确定性地从上游重建**。

### 6.3 推荐的「可确定性重建」脚本（缺失的一环）

当前 `mpv/runtime/` 只能靠人工从官方 ZIP 解压，缺少自动校验。建议新增 `scripts/fetch_mpv_runtime.ps1`：

1. 读取 `mpv/runtime-manifest.json` 的 `artifact_url` 与 `artifact_sha256`；
2. 若本机已有 ZIP 则先校验，否则下载到临时目录；
3. 校验 ZIP 整体 SHA-256；
4. 解压到 `mpv/runtime/`（排除 `README.md` 冲突）；
5. 按清单逐文件复核 SHA-256，任一不匹配即失败退出；
6. 拒绝把任何第三方整合包内容写入该目录。

这样源码仓库对外就是「纯净源码 + 可验证运行时获取方式」，既避免二进制入库，也保证任何协作者/审阅者能一键复现构建前提。

## 7. GitHub 上传策略

### 7.1 仓库现状（已核实）

- 远端：`https://github.com/YasitoliarSaber/KumiPlayer2.0.git`，**公开仓库**；
- 默认分支：`master`；当前工作分支 `codex/backend-v4` **超前 master 152 个提交，master 无独有提交**（可 fast-forward）；
- `.git` 体积：pack 7.38 MiB、对象总数约 8600，仓库极其干净；
- **历史从未提交过任何 `.exe` / `.dll` / `.zip` / `.7z`**（已对全部分支与全部历史核验）；
- 仓库根**没有** `LICENSE` / `COPYING` 文件，`package.json` 与 `Cargo.toml` 也没有 `license` 字段——即 KumiPlayer 自身目前**没有声明许可证**。

### 7.2 是否把 mpv 二进制传到 GitHub

**不要传进 Git。** 按优先级排列可行路径：

1. **首选：不进仓库。** 源码仓库只保留文本与清单，运行时由 `scripts/fetch_mpv_runtime.ps1` 从上游 ZIP + 哈希重建。GitHub 侧不承担 mpv 的再分发角色，GPL 义务的落点仍是「发行安装包的 KumiPlayer」，权责更清晰。
2. **次选：作为 Release 资产分发（不是 git 对象）。** 把 `KumiPlayer-Setup.exe` 挂到 GitHub Releases；如需独立运行时包，可另挂一个 `kumiplayer-mpv-runtime-v0.41.0.zip` 并**同时**附上许可证正文与源码提供承诺。Release 资产不进 Git 历史，可随时替换或删除。
3. **不推荐：直接 `git add` 二进制**（即使有 LFS）。公开仓库一旦提交就成了公开再分发点，GPL 义务立刻生效且不可撤回（历史无法真正删除），还会让每一次 clone 都背上 100 MB。

### 7.3 与「让 GPT 通过 GitHub 插件审阅」的配合

用户需要把分析材料放到 GitHub 上供在线审阅。可行且已具备条件的做法：

- `.gitignore` 已放行 `docs/review/**`，`docs/review/2026-09-15-问题根因与施工方案.md` 已在远程。本文档写入同一目录即可被审阅工具读到；
- 约定：**所有供在线审阅的材料一律走 `docs/review/`，二进制一律不进 Git**；
- 注意分支可见性：默认分支是 `master`，而 `docs/review/` 的文件目前在 `codex/backend-v4` 上。若审阅工具读默认分支，需要把 `codex/backend-v4` 快进到 `master`（152 个提交，属发布级动作，需用户单独决定），或让审阅时显式指定分支。

## 8. 发布包结构建议

### 8.1 安装包内（方案 A，携带内置 MPV）

现状已经合理，`stage_mpv_runtime.ps1` 把源码 `mpv/` 摊平成：

```text
<安装目录>/
├─ tauri-shell.exe
├─ WebView2Loader.dll
├─ runtime/
│  ├─ backend/
│  │  └─ KumiPlayerBackend.exe
│  └─ mpv/
│     ├─ mpv.exe 等 27 个干净运行文件     ← 与 portable_config 同级，符合 mpv portable_config 约定
│     ├─ portable_config/                ← 可替换层
│     ├─ kumiplayer/                     ← 自有层（随包分发）
│     └─ runtime-manifest.json
└─ mirror/
```

**建议在安装包内新增合规材料**（GPL 要求「随包提供」）：

```text
│  └─ mpv/
│     ├─ licenses/                       ← 新增：GPLv2 正文 + 各 DLL 许可证正文
│     │  ├─ LICENSE.GPL-2.0.txt
│     │  ├─ FFmpeg.txt
│     │  ├─ libass.txt / libplacebo.txt / ...
│     └─ THIRD_PARTY_NOTICES.md          ← 新增：组件清单 + 源码提供承诺
```

并在安装器的「关于/许可」入口（或应用的关于页）提供可点击的查看方式。也可以选择把 `licenses/` 放在安装根下，只要**能随包获得**即可。

### 8.2 GitHub Release 资产建议

```text
KumiPlayer-Setup-<version>.exe            # 主安装包
KumiPlayer-<version>-THIRD-PARTY-NOTICES.md
KumiPlayer-<version>-SOURCE-OFFER.txt     # GPLv2 §3(b) 书面源码提供承诺
（可选）KumiPlayer-mpv-runtime-v0.41.0.zip # 仅当需要单独提供内置运行时
（可选）mpv-runtime-v0.41.0.spdx.json      # SBOM，便于审阅与后续升级
```

### 8.3 升到「可发布」所需的最小动作清单

1. 补齐 `mpv/licenses/` 的许可证正文（至少 FFmpeg 的 GPLv2 + 各 LGPL/宽松组件正文）；
2. 扩展 `components-manifest.json`，增加「mpv 运行时组件」段（版本、来源、许可证、随包文件、SHA-256）；
3. 新增源码提供承诺文件（`mpv/SOURCE_OFFER.md` 或 `docs/THIRD_PARTY_NOTICES.md` 的专门章节）；
4. 本机重算原始 ZIP 的 SHA-256 并回填 `runtime-manifest.json`；
5. 把 `distribution_status` 从 `development-only` 改为发布态——**只有前 4 项全部落地后才做这一步**，否则会绕过现有的双层拦截；
6. 复核 FFmpeg 是否为 `--enable-gpl`（本次已核实为是）；若希望降低义务复杂度，可评估未来改用 LGPL 构建，但**当前不建议为此改动**（会牺牲部分硬件解码与功能，且用户已明确要求不改）。

## 10. 风险与未决项

| 项 | 性质 | 处理建议 |
|---|---|---|
| 编解码专利（H.264/H.265/AAC 等） | 独立于 GPL 的风险，无法通过附许可证解决 | 个人/小范围分发按惯例风险极低；商业分发前单独评估 |
| 「书面源码提供承诺」的举证方式 | 合规动作本身简单，但需要有人负责接收并响应请求 | 建议在项目 README 或 Release 说明中给出固定联系方式；只承诺上游源码地址亦可，但需写明有效期 |
| 各组件许可证逐项核对的准确性 | 本文表格中部分条目为「高/中置信度」而非已核实 | 按上游 `mpv-winbuild-cmake` 构建脚本逐项落实，不要照抄本文表格 |
| `master` 与 `codex/backend-v4` 的分支可见性 | 影响在线审阅工具能否读到最新材料 | 需要用户决定是否把 master 快进到当前分支 |
| LGPL 组件的「可替换性」要求 | libplacebo / fribidi / libiconv 等以独立 DLL 形式随包，天然满足「可替换」 | 保持这些 DLL 不被静态链入、不被改名，即维持合规 |
| `distribution_status` 门控被绕过 | 现有脚本已双层拦截，但只能拦「改名或换目录」这类做法 | 保持拦截不变；合规落地后按清单顺序解除 |
