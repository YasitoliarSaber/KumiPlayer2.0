## 0.4 第二轮复核勘误（2026-09-15，必读）

外部审阅对本文件提出 4 条证伪。我已逐条独立复核（源码 + 直接调用生产函数），结果如下：

| # | 原文结论 | 复核结果 | 更正 |
|---|---|---|---|
| 1 | 115 真实样本首行 `\ufeff\|——根目录` 从未被 `_PAN115_ROOT_LINE` 匹配，当前正确路径是"靠巧合" | **原文错误** | 直接调用生产函数 `read_directory_tree_text()` 读 `docs/samples/根目录20260703203700_目录树.txt`：返回文本**不含 U+FEFF**（`_decode_tree_bytes` 对 `FF FE` 选 `"utf-16"`，Python 解码即剥离 BOM），首行 `\|——根目录` 被 `_PAN115_ROOT_LINE.match()` 命中（**True**），解析出 2472 条，相对路径以 `动画/…` 开头。原探针在整段文本上用 `findall` 且未带 `re.M`，属**探针方法错误**，不能作为论据 |
| 2 | OpenList 增量"仍会核对所有目录，`verification_budget` 只影响顺序" | **原文错误** | `incremental.py:258-262` 队列为 `["", *rolling]`，`rolling` 只取最久未验证的 `[:budget]` 个已知目录；只有**新发现或 mtime 明确变化**的子目录才继续入队（`:330-345`）。增量确实受预算限制。真正的缺口是：TXT 基线目录 `modified=None` 导致"首次远端核验"没有状态迁移、`changed` 判定要求前后都非 None、默认预算仅 12（上限 50） |
| 3 | `/api/v4/metadata/retry` 是"确定性空操作" | **表述错误** | `scrape.py:135-177 requeue_work` 只重置 job 状态，但 `process()` 随后**真正重新执行** provider 与图片下载（`scrape.py:285`）。准确说法：重试会真正重跑，它不改变任何输入（配置 / binding / 缓存），因此在故障条件不变时结果必然重复——这正是"点了没变化"的原因；网络或代理恢复后可以成功 |
| 4 | 图 1 的"在线资料服务不可用"与"缺海报"是同一件事 | **过度归因** | `source_unavailable` 产生于 provider 调用异常（`metadata.py:818-837`），artwork 完整性只在 provider 已 ready 之后才运行（`scrape.py:366-391`），是**两个不同阶段**。正确解释见 §1.1 修订说明 |

复核中另外确认了两条原文漏掉的事实：

- **`reason_code` 空值缺口**：`scrape.py:384-391` 在完整性失败时只写 `reason` 与 `completeness`，**没有写 `reason_code`**；而 `service.py:282` 的恢复策略**已经**把 `artifact_incomplete` 列为可重试原因码。补上这个字段就能让 UI 文案与恢复动作立刻正确，不需要改动状态机本身。
- **重试按钮的来源**：`service.py:268-294` 的 fallback 对 `status == "failed"`（`:290-291`）与 `"source_unavailable"`（`:286-287`）都返回 `retry_metadata`，因此这两类作品都会显示「重新获取媒体信息」并真正重跑刮削——与用户观察到的"点了没变化"一致。

## 1. P-01 元数据状态误报：「在线资料服务暂不可用」+「重新获取无变化」

### 1.1 实测数据（用户真实库，只读）

当前活动 revision = `rev-234cb06a…`（confirmed 2026-09-15T08:03:16Z，41 work / 41 mirror / 41 scrape）。实测分布：

| 分类 | 数量 | 状态 |
|---|---|---|
| 番剧（anime_series） | 30 | ready |
| 动画电影（anime_movie） | 6 | ready |
| 动画电影 | **5** | 非 ready |

界面显示的「41 部作品 / 36·5 待处理 / 番剧 30 / 动画电影 6」与之**逐一吻合**。5 部非 ready 全部是动画电影：

| 作品 | TMDB | binding.status | metadata_state | reason | retryable |
|---|---|---|---|---|---|
| 福音战士新剧场版：Q | 75629 | source_unavailable | source_unavailable | 在线资料服务暂不可用，请稍后重试（TMDBClientError） | **true** |
| 天空之城 | 10515 | failed | failed | 海报下载或发布失败；背景图下载或发布失败 | false |
| CLANNAD 剧场版 | 16516 | failed | failed | 海报下载或发布失败；背景图下载或发布失败 | false |
| 魔女宅急便 | 16859 | failed | failed | 海报下载或发布失败 | false |
| 龙猫 | 8392 | failed | failed | 海报下载或发布失败 | false |

5 部的 `metadata_json` 都**包含完整的标题、原名、年份、评分、时长、首播日期、简介、类型**（即用户看到的「刮削结果都是对的」），且 `poster_url` 都是合法的 `https://image.tmdb.org/t/p/w780/…`。

逐目录核对 `data/mirror`：天空之城、CLANNAD 剧场版只有 `clearlogo.png` + `movie.nfo`；魔女宅急便、龙猫、Q 有 `fanart.jpg` + `clearlogo.png`；**5 部都缺 `poster.jpg`**。其余 36 部 ready 作品的 `poster.jpg` 均存在。

**结论：缺的只是海报文件，但状态被写成"在线资料服务不可用"，而「重新获取」虽然会真正重跑刮削，但在故障条件不变时结果必然重复（见 §0.4 勘误 3）。**

**修订说明（原表述过度归因）**：5 部作品其实是**两条不同路径**——

- 福音战士新剧场版：Q 是**真实的 provider 异常**（`metadata.py:818-837` 在 detail 请求抛 `TMDBClientError` 时写 `source_unavailable`）；它之所以仍显示完整资料，是因为 `scrape.py:360-365` 会调用 `_retain_successful_details`，把上一轮成功取得的标题、原名、年份、评分、简介等字段原样保留（`scrape.py:24-61`）。→ **"本轮在线刷新失败" 与 "页面资料完整" 可以同时成立**，UI 应表达为「已保留上次成功获取的资料，本次刷新失败」。
- 另外 4 部（天空之城、CLANNAD 剧场版、魔女宅急便、龙猫）是**资料已经 ready、只有图片产物缺失**，被完整性门控改写成 `metadata_state="failed"`。

### 1.2 根因链

**根因 A：图片产物缺失被写进"资料状态"，且文案统一成服务不可用。**

- `backend/app/media_v4/jobs/scrape.py:366-374`：只有 `metadata_state == "ready"` 才发布产物；
- `scrape.py:376-391`：`assess_metadata_completeness` 不通过 → `metadata_state = "failed"`、`reason = "；".join(reasons)`、`completeness = reasons`，**此时 `reason_code` 仍为空**；
- `backend/app/media_v4/jobs/completeness.py:52-78`：`artwork_storage_mode = "local"` 时，必须存在**已发布且非空**的 `poster` 与 `fanart` 文件，否则返回「海报下载或发布失败 / 背景图下载或发布失败」；
- `backend/app/media_v4/revisions/service.py:83-88`：把 `state == source_unavailable` 映射成「在线资料服务暂不可用，请稍后重试」，把 `state == failed` 映射成「媒体信息处理未能完成，请重试」。

于是"少一张图"在界面上等价于"刮削服务挂了"，与用户看到的完整刮削结果直接矛盾。

**根因 B：图片下载失败被静默吞掉，无法诊断。**

- `backend/app/media_v4/jobs/metadata_artifacts.py:131-174`：poster 是下载循环里的第一个产物，异常在 `151-154` / `168-171` 被吞，既不写 `artifacts` 行，也不落盘、不记日志，只在 completeness 里留下一句中文；
- `metadata_artifacts.py:95-100`：下载客户端用 `proxy=config.proxy_url or None`，http2，超时 3-12 秒；
- 用户 `data/config.json` 的 `proxy_url = http://127.0.0.1:7890`，而**该端口当前未监听**（同一死代理也是本轮 `git push` 与 P-05 的失败背景）；
- 5 部作品的失败集中在第 1、2 个图片请求，第 3 个（clearlogo）全部成功 → 符合"新建客户端后首批请求失败"，而非逐图 404（**具体 HTTP 原因待确认**，本轮未联网复现）。

**根因 C：重试会真正重跑，但不改变任何输入，因此结果必然重复（原文"确定性空操作"表述不准，见 §0.4 勘误 3）。**

- `backend/app/api/media_v4.py:2086-2111` 读取最新 binding 计算 policy；`backend/app/media_v4/jobs/scrape.py:135-177` 的 `requeue_work` **只** `UPDATE jobs SET status='queued'`，不清 binding、不清 `metadata_json`、不改配置；
- provider 是同一 `target` 的纯函数（`scrape.py:285`；`metadata.py:603-612` 走 trusted binding → 同一个 TMDB 请求）；
- 实测：Q 的 scrape job `attempts=2`（08:07:52→08:08:04，其余 40 个 `attempts=1`），binding 于 08:08:04 被重写，结果仍是 `source_unavailable` → **按钮确实执行了，只是结果必然相同**。

**根因 D：图片缺失还导致作品从媒体墙消失。**

- `backend/app/api/library_v4.py:170-172` 只保留 `metadata_state == "ready"` 的作品 → 5 部作品不出现在列表（才有 30+6=36）。

### 1.3 解决办法与施工方案

**P-01a 拆分状态（批次 B1，后端）**

- 保留 `metadata_state` 只表达 provider 身份与资料获取结果；新增**产物状态**（`poster_state` / `fanart_state` / `clearlogo_state` / `nfo_state`，或统一 `artwork_state` + `artifact_errors[]`），持久化进 `scrape_bindings.metadata_json` 与 job 结果；
- `completeness` 失败不再把 `metadata_state` 改写成 `failed`，而是写入 `artwork_missing` 之类的 `reason_code`；
- 前端（`src/components/media/V4ExecutionProgress.tsx:59-76,191-206`）分别展示「资料已获取」与「图片缺失（可重试下载）」，不再出现"服务不可用"。

**P-01b 图片下载可诊断、可重试（批次 B1）**

- 每个产物独立重试（3 次 + 抖动退避），失败写入 `artifacts` 行 `status='failed'` 并记录 `error`（HTTP 状态码 / 超时 / 代理错误）；
- 失败必须进日志与错误日志中心（复用 `core/error_log.py`），不再静默；
- 新增"只重下缺失产物"的恢复动作（`retry_artifacts`），不重跑 provider；重试前清掉该产物的失败缓存，保证输入真的变化；
- 配置面增加「图片源连通性测试」（TMDB API + `image.tmdb.org`），失败时给出可操作提示，例如「本机代理 `127.0.0.1:7890` 不可连接，请启动代理或清空代理设置」（项目已有同类做法：`backend/app/integrations/bangumi.py:313-315`）。

**P-01c 媒体墙可见性（批次 B1，需产品决策，见 §9 决策点 1）**

- 建议：图片缺失**不应**让作品从媒体墙消失；以占位图显示并在卡片上标一个轻微提示。当前 `library_v4.py:170-172` 的 ready 过滤把"导入成功但缺图"变成"作品不见了"。

**P-01d 文案与恢复动作（批次 B1）**

- `service.py:56-89` 的文案映射按新状态重写；`metadata_recovery_action` 增加「重新下载图片」，并保证 `retryable=false` 时前端不渲染必然无效的重试按钮（现状 `service.py:246-250` 对 `episode_not_found(retryable=false)` 仍给 `retry_metadata`）。

**验证（B1）**

- 新增/更新针对性回归：`backend/tests/` 中 completeness、metadata state、artwork 下载、recovery policy 相关用例；用隔离 SQLite fixture，语义覆盖：图片失败 → 资料 ready + 图片缺失；图片重试成功 → 状态收敛；代理不可用 → 提示可操作错误；
- 前端：`src/components/media/V4ExecutionProgress.tsx` 相关组件测试；
- 不修改真实库，用户自行重试验证。

## 2. P-02 来源卡两个数字

### 2.1 「5 个待处理事项」= 真实

- `backend/app/media_v4/projection/source_libraries.py:347-361` `_execution_attention_count`：按作品去重统计 `work_units` 中 `overall_status ∈ {failed, needs_attention}` 的作品数 + 无作品归属的失败 job 数；
- 作品状态由 `backend/app/media_v4/revisions/service.py:430` 推导（`scrape_status not in {ready, confirmed} → needs_attention`）；
- 与只读实测的 5 部非 ready 电影完全一致 → 这个数字是**对的**，问题在 §1 的状态语义。

### 2.2 「11 项关联信息待补全」= 100% 误报

- 计算公式：`source_libraries.py:87-93` 统计 `revision_issues` 中 `code='unresolved_parent_relation' AND resolved=0`，再经 `:364-376` `_relation_is_pending` 只读重估后输出到 `:335`；
- 产生点：`backend/app/media_v4/revisions/service.py:1836-1848`，message 形如「父系列 `series:<key>` 尚未导入，无法建立作品关系」；
- 伪父键来源：**`backend/app/media_v4/resolution/resolver.py:184-190` 对 `child_media_type == "movie"` 且 `relation_type ∈ {movie, spin_off, recap, related}` 强制把父 `media_type` 改成 `"tv"`**，使 `:197-199` 的自名抑制判断（`media_type == child_media_type`）永远不成立 → 生成 `series:<自身标题>:tv`；
- 只读实测：11 条全部形如 `series:龙猫:tv`、`series:天空之城:tv`、`series:福音战士新剧场版:q:tv`，`child` 就是该 active 电影自身（如 `title:龙猫:1988:movie`）→ 父系列永远查不到，永远 pending；
- `git blame`：`184-190` 来自 `074fa46d`，`197-199` 来自 `94bcd53a`（属近期回归）。

### 2.3 解决办法（批次 B2，后端）

1. **修正父关系生成**：电影（`media_type == "movie"`）不应生成父系列关系；自名抑制必须在强制 `media_type` 之前按**规范化标题等值**判断，而不是按 `media_type` 字符串相等；
2. **历史行只读收口**：`_relation_is_pending` 已经是只读重估点，扩展为「child 为 movie 且父键等于 child 自身标题 → 非 pending」，即可让来源卡数字归零，**不需要修改真实库**（符合项目"真实错误数据原样保留"的硬规范）；
3. 回归：`backend/tests/` 中 `unresolved_parent_relation` 与身份关系相关用例；验证 `source_libraries` 卡片计数。

## 3. P-03 识别自动通过率：明显标题也要人工复核

### 3.1 实测复现（与用户截图同症状）

输入：`4k偶像大师 灰姑娘女孩 U149/01.mkv … /12.mkv` + **根目录直属** `SP01.mkv`，`root_container` = 该目录名。

### 3.2 根因

**根因 A：`needs_review` 是文件级布尔标记，与"作品身份是否可得"完全解耦。**

- `backend/app/recognition/media.py:265-273`：非 local/baidu 且路径只有 1 段（例如所选根目录直属的文件）时，作品容器返回 `""`；

即：**12 集正常 + 1 个特别篇文件把整批导入卡死**，而用户认为"名字已经很明显"。

**根因 B：`4k` 前缀不被清洗 → 在线候选永远无法自动采用。**

### 3.3 解决办法（批次 B3）

1. **门控纠偏**：`resolver.py:388-395` 改为「`needs_review` **且** 该条目作品身份不可得」才阻断；`parser.py` 在用选择根目录名成功补出 `series_group`/`title_candidates` 时清除该条目的 `needs_review`；
2. **容器回退**：`media.py:265-273` 在路径只有 1 段时，回退到"本次选择的根目录名"作为作品容器（这是 OpenList/网盘单作品目录的常见形态），而不是返回空；
3. **前置画质前缀清洗**：在标题规范化阶段剥离前置/独立出现的画质 token（`4k/8k/2160p/1080p/uhd/hdr` 等），使本地标题与在线标题可等值；注意保留"标题本身含 4k"的极端情形（可用「剥离后仍能与其他候选等值」作为判定条件，避免误伤）；
4. **issue 分级**：后端给每条 revision issue 增加 `blocking` 字段；前端只对 `blocking=true` 的 issue 禁用确认，非阻断项降级为提示（现状全部靠"issues 非空"一刀切）；
5. **验证**：`backend/tests/test_v4_*.py` 中解析/解析器/候选相关用例 + 新增「根目录直属 SP 文件」「前置 4k 前缀」「单作品目录 OpenList 导入」三个夹具；前端 `tests/components/recognition-identity-dialog.test.tsx` 等同步。

## 5. P-05 OpenList 全量扫描卡死 + 增量与风控

### 5.1 实测数据（用户真实库）

| scan | root | 开始 | 结束 | 耗时 | 结果 |
|---|---|---|---|---|---|
| scan_936 | 夸克 `/夸克网盘/动画` | 08:50:16 | 08:54:20 | **244s** | failed：`OpenList 请求失败（500）` |
| scan_de6 | 同上（gen2） | 09:09:07 | 09:13:11 | **244s** | failed：`OpenList 请求失败（500）` |
| scan_5c8 | 百度 `K:\百度网盘\01动画`（TXT 来源） | 08:03:08 | 08:03:12 | 4s | completed 907 条 |
| scan_751 | 夸克单作品目录 | 09:13:57 | 09:13:59 | 2s | completed 29 条 |

**结论：小目录没问题；大目录整树递归在 244 秒后被 OpenList 上游 500 判失败。界面上表现为"进度卡住不动"，因为读取阶段根本没有百分比。**

### 5.2 根因

1. **读取阶段总量不可知 → 无百分比**：`backend/app/media_v4/sources/scanner.py:590-600`（OpenList full）、`:460-477`（本地）、`backend/app/media_v4/sources/incremental.py:378-382`（增量）都传 `total_count=0`；真正的总量要到扫描返回后才由 `_settle_total`（`source_scan_runner.py:478-489`）写入；`durable_scan.py:402-404` 在 `total==0` 时 `progress=None` → 前端进度条只能是不确定态。
2. **长同步段零进度、零心跳**：`scan_finalize.py:91` 的整批归一化与 `:102-118` 的 `create_draft` 大事务期间不写心跳；心跳只在 `_update_scan_progress`/节流分支里写（`durable_scan.py:131-135`、`source_scan_runner.py:279-284`）。静默超过 120 秒还会被判定为 `interrupted`（`durable_scan.py:397-401`），前端直接提示"上次扫描意外中断"。
3. **单次递归全量列目录 + 限速放大**：每请求间隔 ≥ 1 秒（`integrations/openlist/governor.py:26,70-81`），每页 100 条（`scanner.py:549`），目录数 N 的库读取阶段至少 N 秒且无反馈；全链路没有墙钟超时，唯一总量护栏是 20,000 条（`scanner.py:513-514,552-553`），触发即**整轮失败**。
4. **远端读取阶段没有目录级 checkpoint（原文"失败即全废"表述过头）**：`source_scan_runner.py:458-459` 异常一律落 `failed`，没有部分成功。注意 durable scan **已有** stale recovery：证据完整且已过读取阶段时可从 SQLite evidence 续跑 finalizer，也可用 input archive 重排同一 scan（`source_scan_runner.py:500-610`）；**真正缺的是"最后成功目录 / 下一页游标"**，所以远端读取中断只能从头再来。
5. **增量确实受预算限制（原文"仍会核对所有目录"错误，见 §0.4 勘误 2）**：`incremental.py:258-262` 队列为 `["", *rolling]`，`rolling` 只取最久未验证的 `[:budget]` 个已知目录；只有新发现或 mtime 明确变化的子目录才继续入队（`:330-345`）。真正的缺口是三条：① TXT 基线目录 `modified=None`（`:57-71`），首次远端核验没有"unknown → verified"的状态迁移；② `changed` 判定要求前后都非 None（`:337-341`），因此 `None → 具体 mtime` 不算变化；③ 默认预算仅 12、上限 50（`:29-30,240`），大库首次远端核验需要多轮轮转。
6. **变化判定只比对路径与目录 mtime**（`:331-341,347-371`）：size 与内容指纹都不参与判定；改名等同删+增。建议补 `direct_listing_hash`（对直接子项的 name/is_dir/size/modified 求哈希），避免把网盘 mtime 的稳定性当成唯一依据。
7. **风控可用手段与缺口**：限速 1 req/s（无 burst）、单 worker 串行、`max_entries/max_depth`、冷却（risk_control 6h / rate_limit 1h / 连续 transient 3 次 30min，`sources/health.py:83-89`）；**缺**：无抖动、无每日/每次请求配额头、本地 `openlist_cache` 在扫描路径未被复用（`cache.py` 的 `read_cache` 无调用方；扫描一律 `refresh=False`）、恢复器可能对仍在运行的 scan 重跑 finalizer（`source_scan_runner.py:507-566,568-603`）。

### 5.3 解决办法（批次 B5）

**第一阶段（体验与安全，不改变数据模型）**

1. **读取阶段进度语义**：改为汇报「已列出 N 个目录 / 已获取 M 个文件」的不确定态进度（前端已支持不确定进度条），并每批次写心跳；把 `stage_label` 写成有意义的当前目录；
2. **目录级 durable frontier**：新增 `source_scan_directories(scan_id, remote_path, depth, status, next_page, discovered_at, completed_at)`；发现目录即写入，每完成一页写 `next_page`，目录扫完置 `completed`；worker 从表里取 `queued/scanning` 的下一项，而不是从内存 deque 开始 → 进程重启、断电或风控中断后可以从断点续扫。SourceEvidence 写入必须保持 `(scan_id, source_key)` 幂等（UPSERT / `INSERT OR IGNORE`），避免重读一页产生重复媒体；
3. **目录/请求预算与配额**：每次扫描与每日的目录数与请求数上限（可配置，默认保守），超限时**部分成功**并提示"已扫描 X，剩余 Y 可继续"，而不是整体失败；
4. **上游 5xx 的语义**：识别为「上游存储不可用」，对该 root 冷却一段时间并给出明确提示；对 5xx/超时加**抖动**退避；
5. **复用本地缓存**：目录列举在 TTL 内优先读 `openlist_cache`，把"全量重扫"变成"只打缺失的目录"。

**第二阶段（增量语义，达成用户目标）**

6. **明确两阶段 + 硬预算**：首次必须建立基线（TXT 或一次成功的全量）；之后每轮增量固定「根目录 + 预算内最久未验证的目录」，并把 `verification_budget` 定义为**本轮允许请求的远端目录数上限**（循环内计数，达到上限即停）。同时给基线目录引入 `verification_state: unknown|verified`，`unknown` 目录进入轮转分批核验（受预算约束，不允许为了 UI 百分比一次性递归整棵目录树 —— 那会让请求量翻倍）；
7. **比对字段**：加入 size 与内容指纹（至少 size），避免 mtime 不变但内容替换漏检；
8. **增量变更集**：增量结果应显式区分 added / modified / removed / unverified，并只对变更集生成镜像/刮削任务（现状增量返回"基线克隆 + 本轮观察"的完整集合，会重复生成整批任务）。

**关于用户提出的 WebDAV 思路**

- 代码里已有 WebDAV 入口规范化（`integrations/openlist/client.py:198-199`），但当前浏览与扫描走 `/api/fs/list`；
- WebDAV `PROPFIND Depth:1` 与 `/api/fs/list` 的请求数**基本相同**（都是逐层列举），但 WebDAV 可利用 OpenList 自身的目录缓存；
- **建议**：保留 API 通道（已有 telemetry/限速/冷却治理），把"用户已有目录树"作为**零请求基线来源**（TXT 导入已支持）；OpenList 只承担增量核对。这比"用 WebDAV 抓全树再模拟"更省请求、更安全。

**验证（B5）**

- 后端：`backend/tests/test_v4_scan_closeout.py`、`test_openlist_*`、`test_v4_directory_tree_encoding.py` 等；新增"扫描失败可续扫""超预算部分成功""增量只核对变更目录"三个夹具；
- **不做大库真实全量扫描**（风控红线）；用受控夹具 + 允许用户自己在本机做小范围实测。

| 外壳层裁剪 | 115 固定跳过首层 `根目录` | 粘性标志 `skip_tree_root` 裁掉"栈内首个非空段"（`scanner.py:286,303-305`）；真实 115 样本实测得到 `动画/…`，**与旧实现一致，不是缺陷**。但该标志是**跨全文件的粘性状态**：任何命中 `^\|[—-]{2}(.+)$`（`:34`）或 `^(?:\| )*\|-(.+)$`（`:35`）的行都会置位它 | **脆弱点**：混入 115 风格行的百度树会被多裁一层；应按 provider 显式决定，不用粘性标志 |
| 首行外壳识别 | `pan115.py:258-260` | 生产链路读取后 BOM 已被剥离（`_decode_tree_bytes` 对 `FF FE` 选 `utf-16`），`_PAN115_ROOT_LINE.match(首行)` 实测 **True**，解析出 2472 条、顶层段为 `动画` | **原"BOM 顶掉锚点、靠巧合"结论已撤销**（见 §0.4 勘误 1） |
| `\|` + 两个短横的形态 | — | `^\|[—-]{2}`（`scanner.py:34`）会把 `\|--动画` 匹配成 115 外壳根行并置位上面的粘性标记 | **待样本确认**：真实 115 样本用的是 `\|-`，目前没有 `\|--` 的真实样本可判定影响面 |
| 视频扩展名 | 含 `.rmvb` | `VIDEO_SUFFIXES` 只有 10 个，**无 `.rmvb`**（`scanner.py:123-134`） | **缺陷**：`.rmvb` 会被当目录压栈，污染后续层级 |
| 非视频资源 | 全部产出并带 `resource_hint` | 全部丢弃（`METADATA_SUFFIXES` 声明但无引用，`scanner.py:136-137` 死代码） | 设计取舍，需确认 |
| provider 自动识别 | 按正文连接符**互斥判定**（`media_presets/service.py:796-817`） | **完全没有**，provider 只来自请求（`api/media_v4.py:583-587,1324`） | **能力回退**：用户选错来源时无内容级纠错 |
| 编码兜底 | 百度旧链路 `gbk(errors="replace")` | 全部 strict，失败即报错 | 更严格，可接受 |

### 6.3 施工方案（批次 B6）

1. **按 provider 分支语法、共享路径栈**：`parse_baidu_line()` / `parse_pan115_line()` 各自产出统一的 `TreeNode(depth, name, kind)`，再由共享的 `build_tree_relative_paths()` 建栈；**不要**用跨文件粘性 `skip_tree_root` 表达"跳过外壳根"，而是把 `根目录` 解析成 `kind="root"`，遇到就清栈跳过（百度则完全不跳过）；
2. **不做 BOM 归一改造**（原方案已撤销，见 §0.4 勘误 1）；改为用真实 115 样本做**回归锁定**：断言解析结果以 `动画/` 开头、条目数稳定（当前实测 2472 条）；
3. **恢复正文 provider 探测**：两种格式互斥判定，页面选择与探测结果不一致时给出提示（可作为非阻断警告）；
4. **扩展名表补齐并可配置**：至少补 `.rmvb`，把"视频扩展名"做成单一来源；
5. **非视频资源明确取舍**：要么带 `resource_hint` 保留（旧版行为），要么显式丢弃并写入扫描诊断（当前是静默丢弃）；
6. **回归夹具**：三个真实样本 + 合成边界（无 BOM 的 115、`|--` 变体、含半角 `:` 的条目、超大文件）；
7. 注意 `tree_root.py:92-108` 会因条目含半角 `:` 而**整库拒绝**，需与真实数据核对（全角 `：` 不受影响）。

## 7. P-07 外部 MPV 整合包：可行性与方案

### 7.1 现状事实

- 启动链路唯一：`api/playback_v4.py:74-87` → `media_v4/playback/session.py:103-109` → `playback/mpv.py:53-150` → `playback/mpv_runtime.py:397-470`；
- 实际传入的关键参数（行号均在 `mpv_runtime.py`）：`--config-dir=<KumiPlayer 自己的 portable_config>`（`:424`）、`--include=<kumiplayer/mpv.conf>`（`:426-429`）、`--script=<kumiplayer/scripts/*.lua>`×4（`:430-434`）、`--watch-later-directory`（`:435`）、`--demuxer-cache-dir`（`:436`）、`--log-file`（`:437`）、`--script-opts=thumbfast.thumbnail=…`（`:439`）、`--script-opts=kumiplayer_anime4k.*`（`:441-451`）、`--input-ipc-server`（`:455-456`）、`--start`（`:457`）、`--title`（`:459`）、`--force-media-title`（`:460`）、`--autocreate-playlist=no` 等（`:461-465`）；**未传** `--no-config`、`--input-conf`、`--scripts-append`；
- **没有 `--config-dir` 就等于"不读整合包配置"不成立**：`--config-dir` 是替换语义（本地 `mpv --list-options` 标记 `[not in config files] [file]`，见 [mpv 官方手册](https://mpv.io/manual/stable/)），一旦指定，mpv 不再使用 exe 同级 `portable_config` 与用户 `%APPDATA%\mpv` → **整合包的 `mpv.conf`/`input.conf`/`scripts/` 会被整体绕过**；
- 硬门控：必须存在自有配置目录与自有层（`mpv_runtime.py:247-253`）、4 个自有脚本必须齐全（`:267-277`）、必须能写 `data/mpv-state`（`:417-420`）；`mpv_path` 配置字段仍存在但播放不使用；
- 依赖自有配置的功能中，**只有三处真正依赖配置**：Anime4K（`kumiplayer_anime4k.lua:23,138-141`，且启用时会 `glsl-shaders clr` 清空他人 shader）、截图（脚本强制覆盖 `screenshot-directory/format/template`，`:65,80-82`；且整合包若已绑 F10/Alt+F10，弱绑定必输）、uosc 右键菜单（跨版本可能失效，有降级）；
- **进度、历史、已看状态、自动下一集只依赖 mpv 官方 IPC + 后端 SQLite**（`mpv_runtime.py:455-456`、`session.py:103-131`、`playback/store.py:18-138`），与谁提供配置目录无关 → "用整合包"不会伤到核心功能。

### 7.2 三种架构对比

| 方案 | 对整合包侵入 | 进度/历史/自动下一集 | 截图 | Anime4K | 成本 | 风险 |
|---|---|---|---|---|---|---|
| A 维持现状（唯一内置干净 MPV） | 无（根本不碰） | 全保住 | 全保住 | 保住 | 0 | 不满足"用整合包"诉求 |
| B 外部档 = 整合包 exe + `--config-dir=<整合包>` + `--include` 自有 mpv.conf + 自有脚本 + 状态重定向 | 中（参数不改文件，但覆盖同名项） | 全保住 | 部分失效 | 冲突（清 shader） | 中 | 中 |
| **C 外部档 = 整合包 exe，不传 `--config-dir`**（让 mpv 自发现 exe 同级 `portable_config`）+ 仅追加自有脚本与状态重定向 | **低**（不干预配置选择与脚本生态） | 全保住 | 依赖键位，可能退化为整合包行为 | 外部档不启用自有 Anime4K | 中 | 低-中 |
| D 最小插件集（只注入截图脚本 + 进度 IPC） | 最低 | 全保住 | 可能被覆盖 | 不启用 | 低 | 低，但丢功能 |

### 7.3 推荐：内置为默认 + 可选外部整合包档（外部档零注入）

1. 外部档**不传** `--config-dir`、`--include`、`--script`、`--script-opts`，只传本次会话必需参数：`--input-ipc-server`、`--start`、`--title`、`--force-media-title`、`--save-position-on-quit=no`、`--no-resume-playback`、`--autocreate-playlist=no` + 受控播放列表；
2. 这样 mpv 自行发现并加载整合包的 `portable_config`（`mpv.conf` / `input.conf` / `scripts` / `shaders` / uosc），KumiPlayer 完全不碰该目录，也不修改其中任何文件；
3. **外部档不加载任何 KumiPlayer Lua**：进度、历史、已看状态、自动下一集全部由后端 IPC（`media_v4/playback/session.py:571-642`）与 SQLite 完成，与 Lua 无关；Anime4K 与截图脚本属于**会改变整合包行为**的插件（前者 `glsl-shaders clr`，后者覆盖 `screenshot-directory/format/template` 并占用 F10/Alt+F10），外部档一律不注入；
4. 若将来仍希望外部档提供 KumiPlayer 截图/Anime4K，应做成**默认关闭的可选开关**，并在开关旁明确说明会接管对应行为；
5. 若确实必须注入脚本参数，必须用 `--script-opts-add`（本地 `mpv --list-options` 存在 `-add/-append/-set/-clr/-del/-remove` 变体，说明基础形式是整体设置，直接写会覆盖整合包同名键）；
6. 播放前只做"路径存在 + 可执行"的轻校验（不做内置档的 SHA-256 / 清单门控）；配置模型建议 `player_mode: internal|external` + `external_mpv_path`，旧 `mpv_path` 保留一次迁移；
7. 清理死代码：`playback/mpv.py:205-218`（无人调用的旧契约检查）、`mpv.py:233` 的过期脚本路径；
8. 设置页与首次引导文案改为「播放模式：内置播放器 / 外部 MPV 整合包」，并说明"KumiPlayer 不会修改该目录中的配置或脚本"（`src/pages/FirstRunSetup.tsx:152-162`、`src/pages/SettingsPage.tsx:587-608`、`src/api/config.ts:114`、`api/config.py:398-407,410-429`）。

**合规边界**：加载用户**本地自备**的整合包不等于"从第三方整合包复制配置"（`AGENTS.md` 禁止的是后者）；但不能把该整合包或其组件打进安装包（未补齐许可证与发布材料前只能本地开发）。

**待确认**：`--config-dir`/`--input-conf` 的替换语义、`--script-opts` 的合并语义建议在落地前用 `mpv --list-options` 与本机 v0.41.0 实测复核（本轮只核到了选项存在性与变体）。
