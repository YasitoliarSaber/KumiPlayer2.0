# 项目总体经验教训

> 记录日期：2026-08-23
> 来源：KumiPlayer 项目约三个月的持续开发与多轮技术重构
> 适用范围：AI Agent 协作项目、个人软件项目、需要持续演进的长期项目

## 一句话结论

AI 项目最贵的通常不是一次聊天或一次代码生成，而是方向不清之后反复推倒重来。前期把需求、边界、数据模型和技术路线聊透，往往比后期节省 token 更能节省总成本。

## 一、这次项目暴露出的事实

这个项目满打满算开发了大约三个月，期间技术路线前后重构了四五次。项目初期对 AI Agent 的协作模式几乎没有经验，到现在才逐渐形成了比较清晰的认识。

按项目期间的粗略估算：

- GPT Plus 开了三个账号，费用在 400 元以内；
- OpenCode 开了三个账号，约 100 元；
- 其他中转或辅助服务约 100 元；
- 从项目开始累计消耗约 40 亿到 50 亿 token；
- 如果直接按当前版本的方向实现，估计 10 亿到 20 亿 token 量级就可能够用。

这里最大的差额并不是某一次生成特别浪费，而是前端、后端和整体技术方案反复重做造成的。换句话说，返工把本来可以用于实现功能的额度消耗掉了。

以上金额、额度和次数只是本项目当时的个人记录，不代表任何平台当前的价格、配额或模型能力，也不应直接作为其他项目的预算标准。

## 二、最重要的经验：先把问题定义清楚，再开始写代码

### 1. 需求不清时，代码越快，返工越快

一个长期项目最好先明确：

- 用户到底要完成哪些完整流程；
- 输入从哪里来，可能有哪些来源和形态；
- 系统最终要产生什么结果；
- 哪些能力属于当前范围，哪些明确不做；
- 数据的真实来源是什么，哪些只是缓存、索引或展示层；
- 失败、重试、恢复、迁移和人工修正怎么处理；
- 什么条件算完成，如何验证完成。

如果这些问题没有先形成共同理解，AI 很容易在局部上给出“看起来能用”的方案，但不同局部方案拼起来后，边界、数据流和责任会互相冲突。

### 2. 技术路线要服务完整需求，而不是服务第一个能跑的原型

项目早期采用了比较简单的 TXT 导入思路。后来加入 OpenList 后，输入来源、浏览方式、目录语义和交互范围都发生了变化。OpenList 不是在原有 TXT 流程上简单多一个按钮，而是改变了系统面对“来源”和“目录事实”的方式，因此旧后端很难自然承载，最终不得不重构。

可迁移的判断原则是：

> 如果一个新功能改变了输入模型、核心实体、数据真实来源或主流程边界，就应当按架构变化评估，不能只按普通功能增量处理。

遇到这种情况，先回答“新旧流程是否共享同一个领域模型和事实来源”，再决定是扩展、兼容还是重构。不要因为旧代码已经存在，就强行把新能力缝在旧轮子上。

### 3. “一步到位”不是一次写完，而是一次把方向定对

一步到位不等于一开始就实现所有细节，而是：

1. 先把完整需求和关键场景想清楚；
2. 先确定模块边界、数据流和不可违反的约束；
3. 用一个最小但真实的纵向流程验证路线；
4. 验证通过后再扩大实现范围。

这样可以允许实现分阶段完成，但避免每个阶段都在改变基础假设。

## 三、和 AI 开始工作前，应该先聊透什么

AI 最有价值的阶段不只是写代码，也包括帮助人把模糊想法变成明确方案。正式实现前，至少应与 AI 对齐以下内容：

### 需求层

- 目标用户和最重要的使用场景；
- 主流程、异常流程和人工介入点；
- 成功标准和明确的非目标；
- 第一版必须有的能力，以及可以延后的能力。

### 架构层

- 核心领域对象和它们之间的关系；
- 哪些数据是事实来源，哪些是可重建的缓存；
- 模块的职责边界和依赖方向；
- 外部服务、文件、数据库、播放器或网盘等边界系统如何接入；
- 未来最可能扩展的输入、输出和交互方式；
- 是否需要兼容旧数据、旧 API 或旧执行链。

### 工程层

- 目录和代码组织方式；
- 测试策略与最小验证命令；
- 日志、错误、重试、恢复和迁移策略；
- 哪些操作不可逆，哪些操作必须先预览再确认；
- 什么时候应该停止继续堆功能，回头修正模型或边界。

### 让 AI 先做“方案审查”，再做“代码实现”

可以要求 AI 在写代码前完成以下动作：

1. 复述需求和非目标；
2. 列出关键假设；
3. 指出可能导致大规模返工的设计风险；
4. 提出两到三种技术路线并比较取舍；
5. 推荐一条路线并说明为什么；
6. 给出最小纵向验证切片；
7. 等方案稳定后再拆实现任务。

这一步的价值是把 token 花在降低不确定性上，而不是花在反复修改已经写出来的代码上。

## 四、AI Agent 项目的工作流经验

### 1. 稳定的工作流比堆叠更多工具更重要

项目期间尝试过很多模块化工作流，最后的体会是：工具越多不一定越好，稳定、连续、能保持上下文的工作方式更重要。

当时的实际体验中，GPT Plus 的网页版聊天很适合做持续的需求讨论、方案推演和上下文积累：聊天限制相对少，额度较多，并且曾经有频繁重置额度的体验。与之相比，其他服务可能存在封号风险、网页聊天限制或使用连续性不足的问题。

因此可以把工作拆成三个相对清晰的阶段：

1. **方案阶段**：用连续对话把需求、路线、范围和验收标准讲透；
2. **实现阶段**：让 Agent 按确定的边界逐步改代码，每一步都有局部验证；
3. **复盘阶段**：比较计划、实际改动和验证结果，及时记录架构决策与经验。

网页版聊天适合作为思考和决策空间，代码 Agent 适合作为执行工具。不要让工具本身替代需求判断，也不要为了追求“模块化”而把简单任务拆成互相丢失上下文的多个环节。

### 2. 额度重置会改变经济性，但不应改变技术决策

如果服务的额度会重置，长期使用的性价比可能明显提高；如果不重置，体验和成本判断就会不同。未来是否升级更高档位，也应基于实际的额度消耗、重置规则、稳定性和项目价值来判断。

但这些因素只能影响工具预算，不能反过来决定项目架构。不能因为某个平台额度多，就放弃前期设计；也不能因为额度紧，就用大量补丁掩盖错误的技术路线。工具成本应当服从项目目标，而不是让项目围绕配额设计。

### 3. 先建立“单一事实来源”，再建立并行能力

当新旧流程同时存在时，最容易出现重复模型、重复状态和重复执行链。除非兼容成本经过明确评估，否则不要长期保留两套职责重叠的实现。

新增能力应尽量进入同一套核心数据流，并明确：

- 谁负责产生事实；
- 谁负责把事实变成计划；
- 谁负责执行计划；
- 谁负责生成可重建的索引或展示结果；
- 谁负责处理失败和人工修正。

如果这些问题回答不清楚，继续写更多 UI 或 API 通常只会扩大返工范围。

## 五、下一次项目建议采用的最小流程

### 阶段一：一页项目简报

先写清楚目标、用户、主流程、非目标、输入、输出、约束和验收标准。控制在一页左右，确保任何后续会话都能重新建立共同上下文。

### 阶段二：路线设计

画出核心数据流，定义领域对象、模块边界、事实来源、外部依赖和错误恢复策略。对会影响数据模型或主流程的扩展点提前做假设检查。

### 阶段三：真实纵向切片

不要先做一堆孤立的页面或基础设施。选择一条最能代表真实风险的流程，从输入一直走到最终结果，验证技术路线是否成立。

### 阶段四：分模块实现

每个模块都先写清职责和接口，再实现和验证。局部测试通过不代表整体路线正确，要定期回到完整用户流程检查。

### 阶段五：变更控制

每当出现新想法，先判断它属于：

- 不改变核心模型的普通功能；
- 需要扩展现有模型的能力；
- 改变输入、事实来源或主流程的架构变化。

第三类变化必须先更新路线和边界，再开始代码实现。

### 阶段六：定期复盘

在大功能完成或连续返工出现时，暂停新增功能，检查以下问题：

- 当前实现是否仍然符合最初目标；
- 是否出现多个事实来源或重复执行链；
- 新功能是不是正在被硬塞进不适合的旧模型；
- 继续修补和局部重构哪个总成本更低；
- 当前测试是否真的覆盖了主流程和高风险边界。

## 六、可直接复用的开工检查清单

在让 AI 大规模写代码前，至少确认以下问题：

- [ ] 我能用几句话说清楚产品要解决的问题；
- [ ] 主流程、异常流程和非目标已经写出来；
- [ ] 输入来源和未来可能的输入变化已经考虑；
- [ ] 核心实体、事实来源和缓存边界已经确定；
- [ ] 模块职责和依赖方向已经确定；
- [ ] 新增功能的扩展点不是凭空假设，而是由需求推导出来；
- [ ] 至少有一条真实纵向切片可以验证路线；
- [ ] 已经定义最小验证方式和完成标准；
- [ ] 已经明确哪些数据或操作不可逆；
- [ ] 已经要求 AI 主动指出返工风险，而不是只要求它开始编码。

## 最后总结

这三个月最值得留下的经验，不是某个具体框架、某个 Agent 工具或某个账号组合，而是一个工作顺序：

> 先定义问题，再确定路线；先验证模型，再扩大实现；先保持边界清晰，再追求功能丰富。

AI 可以显著提高实现速度，但它不会自动替人承担方向选择的责任。方向越清晰，AI 越像一支高效的工程团队；方向越模糊，AI 越容易把返工变成高速流水线。Token 只是消耗指标，真正需要管理的是不确定性和返工次数。
